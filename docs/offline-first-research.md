# Offline First для Silentium — исследование и техническое решение

Дата: 2026-09-26. Статус: проект на обсуждение. Код в этой сессии не писался.

---

## 1. Итог: рекомендуемое решение

**Гибридная модель «локальный кеш + очередь записи», а не полноценный offline-first движок синхронизации.**

- Локальное хранилище (IndexedDB через **Dexie**) становится первым источником для чтения на всех экранах.
- Сервер (Supabase Postgres + Drizzle + RLS) остаётся **источником истины** и не меняет схему.
- Записи: оптимистично пишутся в локальную базу и одновременно попадают в **очередь исходящих операций (outbox)**; когда сеть доступна, очередь сбрасывается в существующие Server Actions.
- Чтение: из локальной базы мгновенно, затем фоновое обновление с сервера (stale-while-revalidate).
- Синхронизация: протокол «**полный снапшот данных пользователя с сервера + push outbox'а**». Объём личного дневника мал (тысячи строк ≈ единицы МБ даже за годы), поэтому полноценная инкрементальная репликация на этом этапе не нужна.
- Производные и серверные сущности (серии, XP, AI-память, наставник) локально **не синхронизируются на запись**: серии пересчитываются на клиенте из локальных записей, серверные артефакты приезжают read-only.

Формула этапности: **сначала кеш чтения (закрывает главную боль — медленное открытие), затем очередь записи (закрывает офлайн-ввод), затем экран синхронизации.** Это позволяет остановиться после любого этапа и получить пользу уже от первого.

### Почему не полноценный offline-first движок (RxDB / PowerSync / ElectricSQL / CRDT)

- Все они добавляют инфраструктуру и/или меняют модель доступа к данным. PowerSync и ElectricSQL требуют отдельного сервиса синхронизации поверх Postgres; RxDB тянет собственную реактивную модель и часть возможностей даёт только в платной лицензии.
- Модель данных Silentium для этого не требует: личный дневник одного пользователя, записи почти исключительно append-only, ключ `user_id + entry_date`, уникальность «одна строка на день» (питание) и «одна отметка на день» (аскезы) — это идеальная почва для простого LWW-слияния, а не для CRDT.
- Активных пользователей — единицы (закрытая регистрация по whitelist). Инженерная сложность движка репликации не окупится никогда.

## 2. Подходит ли Silentium для Offline First

**Да, и это редкий случай почти идеального кандидата.**

Аргументы по текущей архитектуре:

1. **Данные уже личные и однопользовательские.** Нет совместного редактирования, нет чужих записей в ленте → конфликтов по природе почти нет.
2. **Записи append-heavy.** Мысли, тренировки, обучение, созидание, досуг, отметки аскез — создаются, почти никогда не правятся, изредка удаляются. Append-only — лучший сценарий для офлайна.
3. **Ключ `entry_date` (локальная дата пользователя) уже вычисляется на клиенте** (`todayLocalDate()` в клиентских компонентах). Локальная запись не зависит от серверных часов.
4. **Уникальные ограничения уже соответствуют upsert-семантике:** `nutrition_user_date_unique`, `asceticism_logs_unique` — повторная синхронизация одной записи идемпотентна.
5. **PK — UUID с `defaultRandom()`.** Если клиент начнёт сам генерировать `crypto.randomUUID()`, существующая схема принимает такие id без единой миграции. Это критично: переход к офлайн-записи не требует менять БД.
6. **Производные таблицы детерминированы.** `day_streaks` и `asceticism_streaks` — чистые функции от истории записей/отметок. Локально их можно считать, а не синхронизировать; сервер продолжит считать своё для авторитетной записи.
7. **PWA-обвязка уже есть.** `public/sw.js` (v3) кеширует навигации (network-first с офлайн-фолбэком) и статику, есть `manifest.ts` и `SwRegistration`. «Офлайн-оболочка» наполовину готова — не хватает только данных.
8. **Боль реальна и подтверждена.** `diagnostics-2026-09-13.md` фиксирует фазовую деградацию канала хост → Supabase (AWS Dublin) по несколько минут — именно тот случай, когда локальный кеш чтения решает проблему пользователя, а не её симптом.

Ограничение, которое нужно принять честно: **наставник (Gemini) офлайн работать не будет** — генерация принципиально серверная (ключ не должен покидать сервер). Офлайн пользователь видит ранее полученные наставления и сообщение «Наставник доступен, когда появится связь». Это осознанная плата, на ценность продукта она не влияет.

## 3. Выбор локального хранилища

| Вариант | Вердикт | Почему |
| --- | --- | --- |
| **LocalStorage** | Только для настроек UI | Лимит ~5 МБ, синхронный API (блокирует поток), только строки, нет индексов. Для журнала непригоден категорически. |
| **IndexedDB напрямую** | Возможен, но не стоит | Низкоуровневый event-based API, много шаблонного кода, нет миграций схемы «из коробки». Писать поверх него свой мини-Dexie — лишняя работа. |
| **Dexie** | **Рекомендуется** | Тонкая (~25 КБ gzip) надстройка над IndexedDB: типизированные таблицы, индексы, версионирование схемы с апгрейдами, транзакции. Зрелый (10+ лет), без реактивной магии, не диктует архитектуру. |
| **Dexie + dexie-react-hooks** | Опционально на этапе 2 | `useLiveQuery` даёт автоматическую перерисовку при изменении локальной базы — сократит код клиентов. Можно добавить позже, интеграционная точка не меняется. |
| **RxDB** | Отклонено | Полноценная репликация + реактивность, но: заметный размер, собственная модель документов, репликация с кастомным backend частично платная. Для снапшот-синхронизации избыточен. |
| **PowerSync / ElectricSQL** | Отклонено | Требуют отдельного сервиса синхронизации и правил репликации поверх Postgres. Инфраструктурная цена несовместима с приоритетом «простота поддержки». |
| **Yjs / CRDT** | Отклонено | Конфликты в личном дневнике — редкость; CRDT-машина не окупается. |

Решение: **Dexie как единственная новая рантайм-зависимость**, LocalStorage остаётся для мелких флагов (тема, статус «синхронизировано», метаданные снапшота).

## 4. Целевая архитектура

### 4.1 Что храним локально (записываемые журналы)

Все журнальные таблицы — **локально в полном объёме пользователя**:

| Таблица | Локальный режим | Слияние |
| --- | --- | --- |
| `thoughts` | read + write | LWW по `updated_at` |
| `training_activities` | read + write | append, удаление по отсутствию в снапшоте |
| `nutrition_entries` | read + write (upsert по дню) | LWW по `updated_at` |
| `learning_entries` | read + write | append |
| `creation_entries` | read + write | append |
| `leisure_entries` | read + write | append |
| `asceticisms` | read + write (создание/деактивация) | LWW по `is_active` |
| `asceticism_logs` | read + write (отметка дня) | LWW, уникальность (asceticism, date) |
| `mentor_messages` (role='user') | write-через outbox | append |
| `mentor_messages` (role='mentor') | read-only | из снапшота |
| `ai_daily_memories`, `ai_periodic_memories` | read-only | из снапшота |

### 4.2 Что НЕ храним локально (остаётся только на сервере)

| Сущность | Причина |
| --- | --- |
| `profiles`, `rpg_profiles`, `xp_events` | Производные/заготовки; `rpg_profiles` читается редко, размер ничтожен. Можно отдавать одним полем снапшота. |
| `day_streaks`, `asceticism_streaks` | **Не синхронизируем вообще.** Локально пересчитываем из журнала (функция уже есть в `lib/asceticism-streak.ts` / `lib/day-streak.ts` — выносится в shared-модуль, доступный обеим сторонам). Сервер продолжает вести свои строки как авторитетный журнал. |
| `mentor_prompts` | Серверная конфигурация, клиенту не нужна. |
| `path_elements` | Статичный справочник из 4 строк — бандлится в код, из БД не тянется. |
| Auth (Supabase), whitelist, `INVITE_KEY` | Серверные по определению. |
| Генерация наставника (Gemini) | Ключ на сервере; офлайн — только кеш прочитанных наставлений. |

### 4.3 Протокол синхронизации (v1 — «снапшот, а не дельты»)

1. **Pull:** один серверный экшен `pullSnapshot()` возвращает все строки пользователя по журнальным таблицам + серверные артефакты (AI-памяти, наставления). Клиент заменяет локальные таблицы, **сохраняя строки, помеченные как pending в outbox** (их локальные версии главнее до успешного push).
2. **Push:** outbox — таблица локальных операций `{ id, table, rowId, op: create|update|delete, payload, baseUpdatedAt, createdAt }`. Сброс идёт по существующим Server Actions; для create в payload передаётся клиентский UUID. Единственное серверное изменение: create-экшены принимают опциональный `id` (uuid-колонки уже принимают любое значение — миграций не нужно).
3. **Идемпотентность:** повторный push одной операции безопасен (upsert по PK, у nutrition/asceticism_logs — ещё и по natural key).
4. **Конфликты:** из-за append-heavy профиля практически возникают только на `thoughts.update` и `nutrition` (два устройства). Правило: LWW по `updated_at`; из outbox передаётся `baseUpdatedAt` (версия строки на момент правки). Если серверная версия новее базовой — конфликт помечается и показывается на экране синхронизации (см. раздел UX); до разрешения по умолчанию побеждает сервер.
5. **Триггеры pull:** первый запуск после чистки хранилища, возврат онлайн (через `navigator.connection`/`online`-событие), открытие приложения (если снапшоту больше N часов), вручную с экрана синхронизации.
6. **Частота push:** сразу при появлении сети и/или с дебаунсом 10–30 с; ручной push — всегда доступен.

Оценка объёма pull: даже 10 лет ежедневных записей — порядка 10–50 тысяч строк, единицы МБ, один ответ JSON. Инкрементальные водяные знаки (`updated_at > last_sync`) оставить как будущую оптимизацию, когда данных станет заметно больше.

### 4.4 Слои кода

- `lib/local/db.ts` — Dexie-схема (версионируемая), зеркальная модель журнальных таблиц.
- `lib/local/sync.ts` — pull/push, outbox, статусы, конфликт-детект.
- `lib/local/repository.ts` (или per-domain файлы) — локальные версии чтения/записи: тот же контракт `Action<T>`, что у Server Actions, поэтому клиентские компоненты меняются минимально.
- Серии: вынести чистые вычисления из `lib/day-streak.ts`/`lib/asceticism-streak.ts` так, чтобы они работали над массивами записей (а не через SQL) — тогда один и тот же код считает их локально и на сервере.
- `components/sync/*` — экран синхронизации в профиле.

Server-side остаётся прежним: те же lib-модули, тот же `withUserDb`, те же Server Actions (единственная правка — приём клиентского `id`).

## 5. Риски и их обработка

| Риск | Серьёзность | Обработка |
| --- | --- | --- |
| **Очистка данных браузером** (главный риск offline-first) | Высокий без мер, низкий с мерами | (а) сервер остаётся источником истины — «потеря» локальной базы = медленный первый pull, не потеря дневника; (б) `navigator.storage.persist()` для защиты от LRU-выселения в Chrome; (в) для Safari — только установленное на домашний экран PWA гарантированно хранит данные (ITP чистит данные сайтов через 7 дней неактивности) → попап «Установи Silentium на домашний экран» на iOS; (г) кнопка «Экспорт резервной копии» (JSON) на экране синхронизации. |
| **Потеря данных** (краш браузера между локальной записью и push) | Низкий | Outbox в IndexedDB транзакционен вместе с самой записью: либо обе операции, либо ни одной. Незасинхронизированное живёт до успешного push. |
| **Повреждение локального хранилища** | Низкий | Индексированные структуры ломаются редко; поведенческая стратегия проста: при ошибке открытия Dexie — удалить базу и полный re-pull (данные не теряются, они на сервере). |
| **Конфликты версий / нескольких устройств** | Средний | LWW по `updated_at` + `baseUpdatedAt`-детект. Append-heavy профиль делает конфликты редкими. Экран синхронизации показывает спорные строки с выбором. Edge-case «правка на A / удаление на B» — по умолчанию побеждает удаление; показать в списке конфликтов, если случился. |
| **Скоук часов устройства** (LWW доверяет меткам времени) | Низкий | Push-операции штампуются сервером при применении; локальная метка используется только для детекта «кто новее» между устройствами. Перекос часов устройства в худшем случае меняет исход редкого конфликта, не целостность. |
| **Истёкший auth-токен офлайн** | Средний | Supabase-сессия живёт ограниченно; офлайн-чтение работает из локальной базы без сервера вообще. Возврат онлайн → refresh токена → push. Если refresh невозможен (пароль сменён) — outbox сохраняется до повторного входа, пользователю показывается «войти, чтобы передать N записей». |
| **Расхождение локальных и серверных серий** | Низкий | Серии не синхронизируются, а вычисляются из одних и тех же записей — расхождение невозможно при одинаковом коде. Серверные строки — журнал для будущего. |
| **Разрастание сложности кодовой базы** | Средний | См. раздел 8: новая подсистема (~1–1.5 тыс. строк) с чёткой границей `lib/local/*`, сервер не усложняется. Главный новый класс багов — рассинхрон кеша; лечится простым протоколом (снапшот, а не дельты). |

## 6. Миграция существующих пользователей

Миграция **серверной части не требует вообще** — схема БД, RLS и миграции Drizzle не меняются. Пользовательский флоу:

1. Пользователь открывает обновлённое приложение (как обычно, онлайн).
2. Локальная база пуста → автоматически запускается первичный pull-снапшот (с индикатором «Переносим хроники на устройство…»). Занимает секунды.
3. Приложение работает. Данных офлайн-миграции «наоборот» (загрузка локальных данных наверх) не существует — сервер всегда был единственным источником.

Нюансы:

- Dexie-схема версионируется (`db.version(n).stores(...).upgrade(...)`) — будущие изменения локальной модели пойдут апгрейдами без re-pull.
- Пулемётная защита: если pull оборвался (плохой канал — он и есть мотивация проекта), повтор делается с нуля или частями по таблицам; протокол идемпотентен.
- Откат решения безопасен: серверные данные не изменяются структурно, отключение фичи возвращает приложение к текущему поведению.

## 7. UX синхронизации

### Принцип: синхронизация молчит, пока всё хорошо

Ручная синхронизация с двумя направлениями — правильная **метафора**, но плохой **режим по умолчанию**: пользователь дневника не должен помнить, куда «передавать хроники». Устойчивая фраза метафоры уже есть в продукте: сервер — это **Башня**, где хранятся **хроники**.

**Режим по умолчанию — автоматический:**
- push — при появлении сети;
- pull — при открытии приложения, если снапшоту больше пары часов, и при возврате после офлайна;
- в профиле — карточка состояния: «Хроники сверены · 5 минут назад» / «N записей ждут передачи…» / «Нужна связь с Башней».

**Ручное управление — одно нейтральное действие в профиле:**

> **«Сверить хроники»** — одновременно push + pull, с понятным результатом («Хроники сверены»).

Кнопки направлений из идеи автора остаются ровно там, где они уместны, — **в разрешении конфликтов** (редкий случай: две версии одной записи). Экран конфликта показывает обе версии и предлагает:

- «Принять хроники Башни» — взять серверную версию;
- «Внести хроники в Башню» — оставить локальную (заменил бы «Передать» — глагол «внести» согласуется с хроникой и записью, а «передать» звучит как пересылка чужого документа).

Так метафора автора сохраняется, но пользователь в 95% случаев не видит её вовсе.

## 8. Усложнение кодовой базы

- **Новое:** `lib/local/*` (Dexie-схема, outbox, sync-движок, репозитории) и экран синхронизации — порядка 1 000–1 500 строк, изолированных в отдельном слое с единственным контрактом наружу («тот же `Action<T>`, что у Server Actions»).
- **Изменяемое:** клиентские компоненты (~10 файлов) переключаются с прямых вызовов экшенов на репозиторий — механическая замена; вычисления серий refactor'ятся в чистые функции.
- **Серверное:** практически не меняется (приём клиентского `id` в create-экшенах). Архитектура, RLS, миграции — нетронутыми.
- **Новый класс сложности:** целостность кеша. Смягчается выбором простого протокола (снапшот) и политикой «локальная база — расходуемый кеш, сервер — истина».

Честная оценка: сложность поддержки вырастет умеренно, но необратимо — offline-first, начавшись, уже не «выключается» простым удалением файла. Это главный аргумент за этапность.

## 9. Оценка объёма работ: **средняя** (с возможностью остановиться рано)

| Этап | Содержание | Объём |
| --- | --- | --- |
| **0. Фундамент** | Клиентские UUID для новых записей; вынос вычислений серий в чистые функции; doc-контракт протокола | S (1–2 дня) |
| **1. Кеш чтения** | Dexie-схема, pull-снапшот, репозитории чтения для всех экранов, фоновое обновление | M (3–5 дней). **Уже закрывает главную боль: мгновенное открытие и устойчивость к плохому каналу** |
| **2. Очередь записи** | Outbox, оптимистичные записи, push при онлайн, приём клиентского `id` на сервере, пилот на «Мыслях», затем остальные разделы | M (4–7 дней) |
| **3. Экран синхронизации** | Статус, «Сверить хранилища», конфликты, экспорт бэкапа, `storage.persist()`, iOS-подсказка об установке | M (3–5 дней) |
| **4. Офлайн-оболочка** | Доведение sw.js до стабильного офлайн-старта, обработка истёкшей сессии, polish, тесты на двух устройствах | S–M (2–4 дня) |

Итого: **средний проект — порядка 2–4 недель** работы одного разработчика с проверками. Он не «большой», потому что: сервер не перестраивается, миграций нет, протокол — снапшот, а не репликация; и не «маленький», потому что появляется новая подсистема состояния с собственным циклом жизни (outbox, конфликты, повреждения кеша) — это нельзя аккуратно сделать за пару дней.

## 10. Внедрять сейчас или отложить

**Рекомендация: начать сейчас, но поэтапно, с правом остановки.**

- **Этап 1 (кеш чтения) — делать сейчас.** Он напрямую лечит заявленную боль («открывается медленно или не открывается»), не меняет модель записи, откатывается удалением фиче-флага и даёт ~80% пользовательской ценности за ~30% труда.
- **Этап 2 (офлайн-запись) — делать следом**, в том же цикле, если этап 1 подтвердил пользу. Это и есть переход к настоящему offline-first.
- **Этапы 3–4 — не откладывать надолго, но и не форсировать:** экран синхронизации нужен, как только появляется outbox (иначе неосинхронизированные записи невидимы — это опасно для доверия к дневнику), а оболочка — по остаточному принципу.

**Аргументы «за сейчас»:** боль подтверждена диагностированной деградацией канала; миграций на сервере нет — цена входа минимальна; данных пока мало, протокол снапшота будет жить долго; пользовательская база мала — риски инцидента ничтожны.

**Аргументы «отложить» (и почему они не перевешивают):** «сначала завершить фичи (XP, расписания тренировок, Nutriarium)» — новые таблицы лягут в локальную схему одной строкой Dexie-версии, откладывание это не упростит; «стабильнее подождать починки канала» — канал внешний, не под нашими контролем, и кеш чтения полезен независимо от него.

**Одна вещь, которую стоит сделать до этапа 2 в любом случае:** убедиться, что все create-пути получают клиентский UUID (этап 0) — это дешёвая подготовка, которая сохраняет свободу выбора «запускать полный offline-first или нет».

## Приложение: вопросы из ТЗ — краткая сводка ответов

1. **Подходит ли Silentium для offline-first?** Да — личный append-heavy журнал, локальные даты, UUID-PK, детерминированные серии, готовая PWA-оболочка.
2. **Хранилище?** IndexedDB через Dexie; LocalStorage — только для настроек; RxDB/PowerSync/ElectricSQL/CRDT — избыточны.
3. **Преимущества перехода:** мгновенное открытие; работа и ввод без сети; устойчивость к деградации канала; снижение нагрузки на пул Supavisor (меньше читающих запросов). **Недостатки:** новая подсистема состояния, необратимость решения, рассинхрон кеша как класс багов, наставник всё равно офлайн не работает.
4. **Риски:** очистка хранилища браузером (главный), конфликты двух устройств, повреждение локальной базы, истёкший токен офлайн. Все обработаны в разделе 5; сервер как источник истины снимает катастрофичность любого из них.
5. **Миграция пользователей:** серверных изменений нет; первый запуск делает автопулл-снапшот; откат безопасен.
6. **Локально:** все журнальные таблицы (мысли, путь, досуг, аскезы и отметки). **Не локально:** производные серии, XP/RPG, AI-памяти и наставник (read-only из снапшота), `mentor_prompts`, auth; `path_elements` — в бандле.
7. **На сервере остаётся:** всё перечисленное выше + роль источника истины и генерация наставника.
8. **Усложнение кодовой базы:** +1 000–1 500 строк в изолированном слое `lib/local/*`; сервер не меняется; клиентов касается механическая замена вызовов.
9. **Объём:** средний (2–4 недели поэтапно), с ранней остановкой после этапа 1.
