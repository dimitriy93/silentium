# Local First: перевод Silentium на локальную базу как единственный источник истины

Дата: 2026-09-27. Предыдущая модель описана в `docs/offline-write-sync-design.md`
(кеш-зеркало + автоматический push/pull). Этот документ фиксирует переход на
модель Local First.

## 1. Что изменилось концептуально

| Было (offline-write-sync) | Стало (Local First) |
|---|---|
| Supabase — источник истины, IndexedDB — кеш-зеркало | Локальная база (IndexedDB/Dexie) — источник истины |
| Автоматический push outbox (дебаунс, таймер ~1 мин, backoff-раннер) | Push только по кнопке «Синхронизировать данные» в Профиле |
| Автоматический pull снапшота при старте, по visibilitychange, по timers | Pull только вручную, после сравнения дат изменений |
| `online`/`offline` listeners, периодические фоновые циклы | Никаких слушателей сети и таймеров |
| «Нет связи с Башней», «Сверяю хроники…» | «Нет связи с сервером», «Выполняется синхронизация», «Синхронизация завершена», «Ошибка синхронизации» |

Пользователь воспринимает приложение как локальный дневник, который иногда
(по его команде) синхронизируется с сервером.

## 2. Архитектурные изменения

### 2.1. SyncProvider переписан (`lib/local/sync-context.tsx`)

Удалено: `runCycle` (push → pull), push-дебаунс 2.5 с, backoff-раннер,
`online`/`offline`/`visibilitychange` listeners, `setInterval(SYNC_THROTTLE_MS)`,
стартовый `runCycle()`, индикаторы «Сверяю хроники…» / «Нет связи с Башней» /
«Хроники отправлены», состояния `syncing/error/online/hydratedBefore`.

Осталось:
- `version` — инкремент после каждой локальной мутации и после загрузки
  с сервера (экраны перечитывают локальную базу через `useCacheQuery`);
- счётчики очереди и dead letter (панель «Повторить»/«Удалить» появляется
  только если сервер отклонил операцию при ручной синхронизации);
- **разовая гидратация**: если локальная база пуста (первый запуск после
  входа — `meta` отсутствует), выполняется один `pullSnapshot`. Без этого
  у приложения нет ни данных, ни `userId` для мутаций. Это единственный
  запрос к серверу при старте, и только пока база не заведена; после неё
  старт не делает ни одного запроса.

### 2.2. Ручная синхронизация

Новые модули:
- `lib/local/manual-sync.ts` — `getLastLocalChange()` (максимум
  `createdAt`/`updatedAt` по журнальным таблицам + `createdAt` операций
  очереди), `pushLocal()` (дренирование outbox батчами по 50 + контрольный
  pull снапшота), `pullIntoLocal()`.
- `actions/snapshot.ts` — `getServerLastChange()`: максимум
  `created_at`/`updated_at` по тем же таблицам на сервере, одним SQL-запросом,
  результат в epoch-миллисекундах (drizzle возвращает сырые значения `sql```как строки формата pg, числовой результат не зависит от парсеров типов).
- `components/sync-section.tsx` — раздел «Синхронизация» в Профиле.

Метрики с обеих сторон совпадают по построению: снапшот копирует серверные
метки времени в локальную базу, push создаёт серверные строки с клиентскими
метками. Поэтому после завершённой синхронизации даты равны байт в байт.

Сценарий кнопки «Синхронизировать данные»:
1. Локальная дата последнего изменения ↔ серверная.
2. Сервер новее → диалог **«На сервере найдены более новые данные»** / «Вы
   можете загрузить данные с сервера на это устройство.» — кнопки
   «Загрузить с сервера» / «Отмена».
3. Локаль новее → диалог **«На устройстве найдены более новые данные»** / «Вы
   можете отправить данные на сервер.» — кнопки «Отправить на сервер» / «Отмена».
4. Даты равны (или обе пусты) → **«Данные уже синхронизированы»**.
5. Сетевая ошибка при сравнении → **«Нет связи с сервером»**; сбой при
   передаче → **«Ошибка синхронизации»**; во время работы → «Выполняется
   синхронизация…» → **«Синхронизация завершена»**.

Загрузка с сервера не теряет несинхронизированные локальные записи:
`writeSnapshot` накладывает оверлей pending-операций outbox поверх снапшота
(механизм из предыдущего этапа сохранён).

### 2.3. Изображения

Новая таблица Dexie **v3** `images` (`lib/local/db.ts`): `{ key, blob,
savedAt, mimeType }`. Модуль `lib/local/images.ts`:
- `getLocalImage(src)` — IndexedDB → (промах) сеть с сохранением blob → null;
- `saveLocalImage(key, blob)` / `deleteLocalImage(key)` — для пользовательских
  загрузок (API готов, UI загрузки в приложении пока отсутствует);
- `useLocalImage(src)` — React-хук, object URL кешируется на жизнь вкладки.

Иллюстрации Пути (`components/path-client.tsx`) переведены с `next/image`
(оптимизатор `/_next/image` требует сервер и не работает офлайн) на `<img>` с
локальными object URL. После первого сетевого захода изображения живут в
IndexedDB и отображаются без интернета и без сервера.

Дополнительно в `public/sw.js` (версия кеша поднята до `silentium-v4`)
`/path/` и `/achievements/` добавлены в cache-first статику.

### 2.5. Меню навигации (`components/bottom-nav.tsx`)

Меню кнопки «+» — горизонтальная панель (`flex flex-row flex-wrap gap-3`)
над нижней навигацией. Каждый пункт — карточка в стиле элементов нижней
панели: круглая иконка (36×36, бронзовый градиент и рамка) сверху, подпись
10px снизу; те же классы `stone-nav`, цвета `--pill-active`/`--gold` и
состояния hover/active. Активный раздел подсвечивается.

## 4. Известные ограничения и решения

1. **Разовая гидратация при первом запуске.** Строгий вариант «ноль запросов
   при старте» не оставляет новому пользователю ни данных, ни `userId` для
   мутаций. Компромисс: пока в локальной базе нет метаданных снапшота,
   выполняется один pull; при офлайне — тихое уведомление «Нет связи с
   сервером — данные не загружены» с кнопкой «Повторить». После первой
   гидратации старт полностью автономен.
2. **Навигация офлайн работает через SW-кеш страниц** (network-first с
   фолбэком): страница доступна без сети, если открывалась ранее при сети.
   Непосещённые страницы офлайн не откроются — это свойство PWA-архитектуры,
   не изменившееся в этой миграции.
3. **Конфликт «новее и там, и там»** решается в пользу предложения загрузки
   с сервера (pending-операции переживают снапшот и остаются в очереди для
   следующей ручной отправки).
4. **Наставник** (`/mentor`) по-прежнему требует сети (Gemini) — это
   осознанное серверное действие, не часть локального дневника.
5. В тестовой базе осталась строка «Серверная запись: проверка загрузки
   с сервера» (тестовый аккаунт `test@silentium-app.dev`) — артефакт
   проверки загрузки с сервера.
