# Silentium — Этап 2: Offline-запись и синхронизация. Технический проект

Дата: 2026-09-27. Статус: проект на обсуждение. Код в этой сессии не писался, миграции не выполнялись.

Предмет: механизм записи данных при недоступности сервера и последующей автоматической
синхронизации. Опирается на реализованный Этап 1 (кеш чтения: `lib/local/*`,
`hooks/use-cache-query.ts`, `actions/snapshot.ts`) и на исследование
`docs/offline-first-research.md`. Реализация Этапа 1 не пересматривается — Этап 2
надстраивается над ней.

Главный принцип: **простое → надёжное → понятное → достаточное**. Это персональное
приложение с малым объёмом данных; никаких CRDT, векторов версий и универсальных
движков репликации.

## 1. Архитектура Этапа 2

### 1.1. Идея

Этап 1 сделал кеш первым источником **чтения**. Этап 2 делает его первым источником и
**записи**: любая мутация пользователя пишется локально (мгновенно отображается) и
одновременно ставится в **очередь исходящих операций (outbox)**. Отдельный цикл
синхронизации периодически выталкивает очередь на сервер и подтягивает снапшот обратно.

```
мутация UI
   ↓
оптимистичная запись в кеш + enqueue в outbox   ← интерфейс обновился мгновенно
   ↓
push-цикл (когда есть сеть): outbox → сервер
   ↓
подтверждение → операция удаляется из outbox
   ↓
pull-цикл: снапшот сервера → кеш (pending-строки не затираются)
   ↓
version++ в SyncProvider → экраны перечитывают кеш
```

### 1.2. Единый путь записи

Все мутации пользователя идут **всегда** через outbox — и онлайн, и офлайн. Онлайн
очередь опустошается за секунды, и это неотличимо от сегодняшнего поведения; офлайн
операции просто ждут. Одна кодовая дорожка вместо двух («прямая запись при сети +
отдельная офлайн») — это главная упрощающая развилка проекта:

- один набор UX-состояний, один источник ошибок записи;
- один серверный контракт приёма операций (см. раздел 6);
- невозможно «забыть» офлайн-ветку в каком-нибудь экране.

Существующие Server Actions (`actions/thoughts.ts`, `actions/path.ts` и т.д.) **не
изменяются**. Новые вызовы идут мимо них — через новый экшен приёма очереди,
переиспользующий тот же lib-слой (`lib/thoughts.ts`, `lib/path.ts`, …). Со временем
мутационные экшены можно будет убрать; сейчас они остаются как есть.

### 1.3. Слои

| Слой | Что делает | Новое/существующее |
| --- | --- | --- |
| Экраны (`*-client.tsx`) | вызывают enqueue вместо Server Actions; читают кеш как сейчас | переписываются точечно |
| `lib/local/outbox.ts` | enqueue, чтение очереди, статусы, счётчики | **новый** |
| `lib/local/sync-runner.ts` (логика внутри `sync-context.tsx`) | push- и pull-циклы, backoff | **новый** (расширение SyncProvider) |
| `lib/local/writes.ts` | + оверлей pending-операций поверх снапшота | расширяется |
| `actions/sync.ts` | `pushOutbox(ops)` — приём очереди на сервере | **новый** |
| lib-слой (`lib/thoughts.ts` и др.) | принимают опциональные `id`, `createdAt`, `clientUpdatedAt` | минимальные сигнатурные дополнения |
| Supabase / Drizzle схема | **без изменений** | — |

### 1.4. Что остаётся только серверным

- Серии (`day_streaks`, `asceticism_streaks`), XP, AI-памяти, наставник — сервер
  пересчитывает их из журнала при push, как делает сегодня для прямых мутаций.
  Локально они только читаются из снапшота (или пересчитываются для отображения —
  как уже делает экран аскез). В outbox они не попадают.
- Наставник офлайн недоступен (генерация серверная) — как и зафиксировано в
  исследовании. Если позже появится запись пользовательских сообщений в
  `mentor_messages`, она встраивается в outbox ещё одной сущностью, ничего в ядре
  не меняя.

## 2. Схема IndexedDB

База `silentium` (Dexie) получает **версию 2** — добавляется одна таблица `outbox`.
Существующая схема (таблицы кеша, `meta`, `dayStreak`) не меняется; апгрейд пустой
(новая таблица создаётся автоматически), re-pull не требуется.

```
silentium v2
  thoughts            "id, entryDate"                (как в v1)
  training            "id, entryDate"                (как в v1)
  nutrition           "id, entryDate"                (как в v1)
  learning            "id, entryDate"                (как в v1)
  creation            "id, entryDate"                (как в v1)
  leisure             "id, entryDate"                (как в v1)
  asceticisms         "id"                           (как в v1)
  asceticismLogs      "id, entryDate, asceticismId"  (как в v1)
  asceticismStreaks   "id, asceticismId"             (как в v1)
  dayStreak           "key"                          (как в v1)
  meta                "key"                          (как в v1)
  outbox              "++seq, opId, status, entity, rowId"   ← НОВОЕ
```

Индекс `++seq` (автоинкремент) — первичный ключ: строгий порядок применения операций
задаётся вставкой, сортировка не нужна. Остальные индексы служат статус-запросам
(`status`) и оверлею pending-строк (`entity + rowId`).

## 3. Схема outbox

```ts
interface OutboxEntry {
  /** Автоинкремент — первичный ключ; порядок операций = порядок вставки. */
  seq: number;

  /** UUID самой операции (crypto.randomUUID) — для трассировки и ответов сервера. */
  opId: string;

  /** Кто создал операцию. Защита при смене пользователя: чужие операции не пушатся. */
  userId: string;

  /** Сущность. */
  entity: "thought" | "training" | "nutrition" | "learning"
        | "creation" | "leisure" | "asceticism" | "asceticismLog";

  /** Тип операции (см. раздел 4). */
  op: "create" | "update" | "delete" | "upsert";

  /** Клиентский UUID строки. Для nutrition/asceticismLog локальная строка тоже
   *  получает uuid — даже если сервер при upsert-конфликте вернёт другой (см. 7.5). */
  rowId: string;

  /** Данные операции: ПОЛНЫЙ набор редактируемых полей (не дифф), формат —
   *  сериализуемая форма строки без серверных timestamp'ов. Для delete — null. */
  payload: Record<string, unknown> | null;

  /** ISO: время операции на клиенте (для create — будущий created_at строки). */
  createdAt: string;

  /** pending → sending → (удалена | failed). */
  status: "pending" | "sending" | "failed";

  attempts: number;
  lastAttemptAt: string | null;
  error: string | null;
}
```

Состав `payload` по сущностям:

| entity / op | payload |
| --- | --- |
| thought create | `{ id, entryDate, content, createdAt }` |
| thought update | `{ id, content, clientUpdatedAt }` |
| thought delete | — |
| training create | `{ id, entryDate, title, detail, durationMinutes, createdAt }` |
| training delete | — |
| nutrition upsert | `{ id, entryDate, calories, proteinGrams, fatGrams, carbsGrams, note, clientUpdatedAt }` |
| learning / creation create | `{ id, entryDate, content, createdAt }` |
| learning / creation delete | — |
| leisure create | `{ id, entryDate, title, minutes, notes, createdAt }` |
| leisure delete | — |
| asceticism create | `{ id, title, description, startDate, createdAt }` |
| asceticism update | `{ id, title?, description?, isActive?, clientUpdatedAt }` |
| asceticism delete | — |
| asceticismLog upsert | `{ id, asceticismId, entryDate, status: "done" \| "failed" \| "none", clientUpdatedAt }` |

Принципы:

1. **Payload — полное состояние, а не дифф.** Повторная отправка и сжатие очереди
   становятся безопасными по построению.
2. **Сжатие очереди не делаем.** Операции применяются сервером в порядке `seq` — это
   всегда корректно (реплика журнала). Сжатие «update+update → последний» —
   возможная будущая оптимизация, не закладываем её в контракт.
3. Статус `done` не хранится: подтверждённая операция **удаляется** из очереди.

## 4. Типы операций

Множество операций выведено из реально существующих мутаций экранов (проверено по
`actions/*.ts`): ничего лишнего, ничего выдуманного.

| op | Семантика | Кто использует |
| --- | --- | --- |
| `create` | вставка строки с клиентским UUID | мысли, тренировки, обучение, созидание, досуг, аскезы |
| `update` | правка полей существующей строки | мысли (текст), аскезы (название/описание/is_active) |
| `delete` | удаление по id | все журнальные сущности, аскезы (каскад на отметки/серии остаётся серверным) |
| `upsert` | вставка-или-обновление по natural key | питание (по дню), отметки аскез (по паре asceticism+день) |

Что **не** вводим и почему:

- `toggle / mark` как отдельный тип — не нужен: отметка аскезы это `upsert`
  (`status: done|failed|none`, где `none` сервер трактует как «снять отметку»,
  как сегодня в `setAsceticismLog`), переключатель `is_active` аскезы — `update`.
- Отдельного `upsert` для других сущностей нет — у них нет natural key.
- Операций для серий, XP, AI-памятей, наставника — нет (раздел 1.4).

## 5. Алгоритм push

Триггеры: событие `online`, возврат вкладки, после каждого enqueue (с дебаунсом ~2–3 с
и малой задержкой, чтобы сгруппировать быстрые операции в один батч), периодически при
открытом приложении (таймер ~1 мин), вручную. Все триггеры сходятся в один раннер в
`SyncProvider` — рядом с уже существующей pull-логикой Этапа 1.

```
push():
  1. если offline, уже выполняется push, или очередь пуста — выйти.
  2. взять из outbox все ops со status ∈ {pending, failed} в порядке seq,
     кроме тех, чей backoff ещё не истёк. Батч ≤ 50 операций (дальше — в следующий заход).
  3. пометить их status = "sending".
  4. pushOutbox(ops) →  сервер возвращает по каждой операции { opId, ok, error? }.
  5. для ok-операций: удалить из outbox.
     для операций с ошибкой валидации/состояния (не сетевой): status = "failed",
     error = текст, attempts + 1. Если attempts ≥ MAX (10) — остаётся failed
     навсегда (dead letter, показывается пользователю, есть «Повторить»/«Удалить»).
     сетевой сбой батча целиком: все sending → pending, backoff = min(1мин·2^n, 1час).
  6. если хотя бы одна операция применилась — форсировать pull (раздел 7).
```

Свойства:

- **Порядок гарантирован** одним устройством (`seq`); сервер применяет операции
  последовательно в полученном порядке.
- **Полу-атомарность батча:** сервер применяет операции по одной, ошибки одной
  операции не откатывают соседние. Транзакция на уровне одной операции достаточно
  (внутри — мутация + пересчёт серии дня).
- **Смена пользователя:** перед отправкой из батча выбрасываются операции с
  `userId ≠ текущий пользователь` (и удаляются из очереди — они больше не имеют смысла).

## 6. Изменения Server Actions / API

Новый файл `actions/sync.ts` — единственная серверная надстройка:

```
pushOutbox(ops: OutboxOp[]): Promise<Action<PushResult[]>>
```

- авторизация через `getCurrentUser()`; для каждой операции — та же zod-валидация, что
  в существующих экшенах (схемы переиспользуются/дублируются из них);
- диспетчер по `entity`/`op` вызывает **существующие функции lib-слоя**
  (`dbCreateThought`, `dbUpsertNutrition`, `dbSetAsceticismLog`, …) — бизнес-логика,
  включая `syncDayStreak` и каскад аскез, живёт в одном месте и не дублируется;
- результат — пооперационный: `{ opId, ok: true }` или `{ opId, ok: false, error }`.
  `revalidatePath` — один раз на батч по затронутым разделам.

Минимальные изменения lib-слоя (сигнатурные, не ломающие текущих вызовов):

1. **create-функции принимают опциональные `id` и `createdAt`** — если переданы,
   пишутся явно; иначе остаются `defaultRandom()` / `now()` (существующие вызовы
   работают как раньше).
2. **update-функции принимают опциональный `clientUpdatedAt`** — пишется в
   `updated_at` вместо `now()` (с клампом: будущее время прижимается к серверному
   `now()`). Это основа LWW-разрешения конфликтов (раздел 8).
3. **create-вставки получают `onConflictDoNothing({ target: id })`** — идемпотентность
   повтора (раздел 9).

`pullSnapshot` (Этап 1) остаётся без изменений. Никаких новых таблиц в Postgres,
никаких миграций.

## 7. Алгоритм pull и полный цикл синхронизации

### 7.1. Pull

Существующий `pullSnapshot` + `writeSnapshot`, плюс один новый шаг — **оверлей
pending-операций**:

```
pull():
  1. pullSnapshot() с сервера.
  2. writeSnapshot(): полная замена кеша — как сегодня.
  3. ОВЕРЛЕЙ: для каждой операции в outbox со status ∈ {pending, sending, failed}
     переписать соответствующую строку кеша из payload
     (upsert строки по rowId; для delete — удалить строку).
  4. version++ в SyncProvider.
```

Оверлей нужен, потому что снапшот сервера не знает о ещё не отправленных локальных
операциях. Он идемпотентен и дёшев (pending-операций единицы). Шаг 3 выполняется в той
же транзакции, что и writeSnapshot.

### 7.2. Полный прямой цикл (сценарий из постановки)

```
интернет пропал
→ пользователь записывает мысль
→ enqueue: payload {id: clientUUID, entryDate, content, createdAt} + оптимистичная
  запись в таблицу thoughts кеша → интерфейс показал запись мгновенно (version++)
→ операция ждёт в outbox (status = pending)
→ интернет появился (событие online / возврат вкладки)
→ push(): pushOutbox → сервер валидирует, вставляет строку с КЛИЕНТСКИМ id и
  клиентским createdAt, пересчитывает серию дня
→ { opId, ok: true } → операция удалена из outbox
→ форс-пулл: снапшот подтверждает запись, оверлей пуст → кеш = сервер
→ version++ → интерфейс перечитал кеш
```

### 7.3. Порядок «push перед pull»

Каждый цикл синхронизации всегда делает сначала push (если очередь непуста), затем
pull. Так кеш после цикла гарантированно отражает и локальные изменения, и сервер.

### 7.4. Обратный цикл (сервер новее)

Уже реализован Этапом 1: триггеры pull (`online`, видимость, открытие), снапшот
заменяет кеш, `version++` обновляет экраны. Этап 2 добавляет только оверлей (7.1) —
pending-строки пользователя переживают снапшот до момента подтверждения их push'ем.

### 7.5. Особый случай: nutrition и отметки аскез

Upсert по natural key может вернуть строку, чей PK отличается от клиентского uuid
(например, питание за день создано на другом устройстве). Это не проблема: UI читает
питание по `entryDate`, отметки — по паре asceticism+день, идентификатор строки на
экранах не используется. Расхождение PK живёт до следующего снапшота и исчезает в нём.

## 8. Разрешение конфликтов

### 8.1. Реестр сценариев

| Сценарий | Механизм | Результат |
| --- | --- | --- |
| Один пользователь, одно устройство | outbox = реплика журнала, порядок `seq` | конфликтов нет по построению |
| Несколько устройств, разные записи | ничего не требуется | оба изменения встают на сервер |
| Два устройства правят одну запись | LWW по `updated_at` (клиентский `clientUpdatedAt`) | побеждает последняя правка |
| Два устройства пишут питание за один день | upsert по natural key + LWW | побеждает последний push |
| Два устройства отмечают аскезу за один день | upsert по (asceticism, date) + LWW | побеждает последний push |
| Удаление на A, правка на B | правка удалённой строки — UPDATE 0 строк, операция считается применённой | побеждает удаление |
| Create на A, create той же записи на B | невозможно: UUID уникален, дублей нет | — |

### 8.2. Правило

**LWW по `updated_at` + «удаление побеждает правку» + клиентские UUID.** Три механики,
все уже почти поддержаны схемой. Двухзначный выбор осознан: в личном дневнике
«кто последним записал, тот и прав» — ожидаемая семантика, а редкая потеря правки при
параллельном удалении принимается (персональные данные, единый пользователь, записи
мелкие). Тумбстоуны и экран слияния — не строим; при желании позже можно добавить
уведомление «правка не применилась, запись была удалена на другом устройстве» —
точка расширения: операция update, вернувшаяся с признаком `not-applied`.

Порядок применения гарантирует отсутствие промежуточных повреждений: сервер всегда
находится в консистентном состоянии, расхождение существует только между устройствами
до следующей синхронизации.

## 9. Идемпотентность

Сценарий: операция отправлена, сервер её применил, ответ потерян (обрыв сети на
последнем шаге). Клиент помечает операцию обратно в `pending` и рано или поздно
отправит её повторно.

Идемпотентность обеспечивается **естественными ключами**, без реестра обработанных
`opId` (не нужна новая таблица Postgres):

| op | Повтор на сервере | Почему безопасно |
| --- | --- | --- |
| create | `INSERT … ON CONFLICT (id) DO NOTHING` | тот же клиентский UUID → вторая вставка ничего не делает |
| update | `UPDATE … WHERE id AND userId` | payload полный → повтор перезаписывает тем же содержимым; `clientUpdatedAt` не меняется, LWW не сдвигается |
| delete | `DELETE … WHERE id AND userId`; 0 строк = успех | повтор удаляет ничего |
| upsert | существующий `onConflictDoUpdate` по natural key | повтор перезаписывает тем же содержимым |

Дополнительно: повторный push подряд идущих операций ничего не ломает, потому что
порядок сохранён и каждая операция полная (раздел 3). `opId` используется только для
трассировки и пооперационных ответов, в идемпотентности не участвует — это упрощение
осознанное.

## 10. Безопасность данных

| Ситуация | Поведение |
| --- | --- |
| **Смена пользователя на устройстве** | Операции outbox несут `userId`. Операции другого пользователя при push выбрасываются и удаляются. `writeSnapshot` уже стирает чужой кеш — то же правило распространяется на очередь: при записи снапшота с новым `userId` outbox очищается. |
| **Выход из аккаунта** | При sign-out: если очередь непуста — подтверждение «N записей ещё не отправлены и будут потеряны». После подтверждения (или при пустой очереди) — локальная очистка: кеш (уже есть) + outbox + meta. |
| **Очистка локальных данных** | `Dexie.delete("silentium")` — однострочный полный сброс (кеш + очередь). Следующий вход делает свежий pull. |
| **Повреждение IndexedDB** | Все обращения уже обёрнуты в try/catch и не ломают экран. Для outbox это риск потери данных, а не просто кеша: повреждённая база пересоздаётся, **неотправленные операции теряются**. Признаваемое ограничение; смягчение — очередь почти всегда пуста (push при каждом enqueue онлайн). |
| **Переустановка PWA / очистка хранилища браузером** | Эквивалент очистки данных: кеш восстановится пуллом; неотправленные операции потеряны. Единственная реальная дыра loss-модели; принимается (альтернатива — серверная буферизация неаутентифицированных операций, не окупается для персонального приложения). |
| **Несколько устройств** | Каждое устройство имеет свою очередь и свой кеш; согласование — через сервер (LWW + снапшот). Устройства не общаются друг с другом. |
| **Истёкшая сессия при офлайне** | Push вернёт «Требуется авторизация»: операции остаются pending, показывается нейтральный статус. После повторного входа тем же пользователем push продолжается. Не считаем ошибкой очереди. |
| **Две вкладки одного устройства** | IndexedDB сериализует записи — очередь одна и корректна. Двойной push возможен, но безопасен (идемпотентность, раздел 9); простое защитное «sending в пределах вкладки» достаточно, межвкладочная блокировка не нужна. |

## 11. UX-состояния (только описание, UI не строится)

Стилистика сохраняется: бронза, приглушённые подписи, «Башня» = сервер, «хроники» =
записи. База — существующий индикатор SyncProvider, расширяется статусами очереди.

| Состояние | Что видит пользователь |
| --- | --- |
| **Онлайн, всё синхронизировано** | Ничего. Тишина — нормальное состояние; никаких постоянных бейджей. |
| **Офлайн** | Тихий постоянный индикатор внизу (рядом с навигацией): точка-«угасание» + «Нет связи с Башней — записи сохраняются на устройстве». Появляется/исчезает без анимационного шума. |
| **Есть несинхронизированные изменения** | 1) На самих записях — маленькая бронзовая метка (точка/перо) у ещё не отправленных. 2) В индикаторе (или в настройках) — «N хроник ждут отправки». Счётчик по outbox (pending + failed). |
| **Идёт синхронизация** | Существующий индикатор «Сверяю хроники…»; при непустой очереди — «Отправляю хроники…». Как сейчас: только если данные уже гидратированы. |
| **Синхронизация завершена** | Тихо. Допустимо короткое «Хроники отправлены» (2–3 с) после батча, закрывшего длинную офлайн-сессию. |
| **Синхронизация не удалась** | Два уровня. Сетевой сбой — индикатор «Не удалось отправить хроники, повторю позже» (авто-retry с backoff). Операция отклонена сервером / исчерпаны попытки — инлайн-подпись у записи («не удалось отправить») с действиями «Повторить» и «Удалить локально». Это dead-letter, отдельного экрана синхронизации на данном этапе не строим. |

Принципы: состояния не спорят между собой (офлайн + pending показывается одним
индикатором), ничего не блокируется — записи можно продолжать создавать, ошибки не
пугают («запись сохранена на устройстве» — всегда правда).

## 12. План реализации по небольшим этапам

Каждый шаг оставляет приложение полностью рабочим и откатываемым.

| Шаг | Содержание | Проверка |
| --- | --- | --- |
| **2.1. Outbox-инфраструктура** | Dexie v2 (+ таблица `outbox`), типы, `lib/local/outbox.ts` (enqueue/чтение/статусы). Поведения экранов не меняется | сборка, smoke: кеш Этапа 1 жив, апгрейд v1→v2 без re-pull |
| **2.2. Клиентские UUID** | create-функции lib-слоя принимают опциональные `id`/`createdAt`; существующие экшены — тоже (обратная совместимость); клиенты генерируют UUID при создании. Запись ещё идёт старым потоком | онлайн-поток не изменился визуально; в БД строки с клиентскими UUID |
| **2.3. `pushOutbox` + идемпотентный lib-слой** | `actions/sync.ts`, onConflictDoNothing на create, `clientUpdatedAt` в update, валидация как в существующих экшенах | батч операций применяется, повторная отправка не создаёт дублей |
| **2.4. Оптимистичная запись через outbox** | Мысли (первый экран): enqueue + локальная запись в кеш + мгновенный push при сети; ack → подтверждение. Затем остальные экраны по одному | «интернет пропал → запись видна → интернет появился → запись на сервере» |
| **2.5. Pull с оверлеем** | Pending-операции переживают снапшот; порядок push→pull в SyncProvider | правка не теряется при снапшоте до отправки |
| **2.6. UX-состояния** | Индикаторы раздела 11, счётчик pending, dead-letter с «Повторить/Удалить», backoff | все шесть состояний проверяются вручную (DevTools offline) |
| **2.7. Безопасность и краевые случаи** | sign-out с подтверждением, очистка outbox при смене пользователя, истёкшая сессия, две вкладки, переустановка | чек-лист сценариев раздела 10 пройден |

Порядок принципиален: 2.2 самодостаточна и полезна даже без остального (это и есть
«этап 0» из исследования), 2.4 можно останавливать после любого экрана.

## 13. Риски

| Риск | Вероятность | Смягчение |
| --- | --- | --- |
| Потеря неотправленных операций при очистке хранилища (reinstall, eviction браузером) | низкая (очередь почти всегда пуста) | принят осознанно; push сразу после enqueue; в UX честная формулировка |
| Дрейф/перевод часов устройства портит LWW и сортировку | низкая; средняя при ручной правке часов | кламп будущего `clientUpdatedAt`/`createdAt` к серверному `now()`; сортировка внутри дня ведётся по `createdAt`, а он клиентский и монотонный в рамках сессии |
| `pushOutbox` расходится с существующими экшенами (забыт side-effect, другая валидация) | средняя, главный риск сопровождения | диспетчер переиспользует lib-слой и zod-схемы существующих экшенов; новые поля — опциональные; экраны переключаются на outbox по одному |
| FK-отказ: отметка аскезы, чья аскеза ещё не применилась на сервере | возможна только при failed create | порядок `seq` даёт parent-first; при dead-letter родителя дочерняя операция тоже уходит в failed с понятной ошибкой |
| Незакрытая гонка push из двух вкладок | безопасна по построению | идемпотентность (раздел 9); статус sending — per-tab |
| Апгрейд Dexie v1→v2 у существующих пользователей | низкая | пустой апгрейд, покрыт smoke-проверкой шага 2.1 |
| Рост очереди при долгом офлайне (сотни операций) | малые данные, но возможно | батч ≤ 50, payload полные, но компактные; сжатие очереди — задел на будущее, не нужен в v1 |

## 14. Оценка сложности

| Шаг | Оценка |
| --- | --- |
| 2.1 Outbox-инфраструктура | 0.5–1 день |
| 2.2 Клиентские UUID | 0.5–1 день |
| 2.3 pushOutbox + идемпотентный lib-слой | 1–1.5 дня |
| 2.4 Оптимистичная запись через outbox (все экраны) | 2–3 дня |
| 2.5 Pull с оверлеем | 0.5–1 день |
| 2.6 UX-состояния | 1–2 дня |
| 2.7 Безопасность и краевые случаи + ручная проверка сценариев | 1–1.5 дня |
| **Итого** | **≈ 6.5–11 рабочих дней** |

Сложность поддержки после завершения растёт умеренно и необратимо (как зафиксировано
в исследовании), но ядро остаётся компактным: одна таблица IndexedDB, один серверный
экшен, три механики согласованности (клиентские UUID, LWW, идемпотентные повторы).
Альтернативные «движки» по-прежнему не нужны.
