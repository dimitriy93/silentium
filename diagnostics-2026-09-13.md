# Диагностика слоя БД — этап 2.5 (13 сентября 2026)

Результаты раскопок, чтобы не повторять их в следующей сессии.

## Итоговая картина

Три независимых слоя проблем, проявлявшихся как «случайные зависания страниц»:

1. **Баг postgres.js** (драйвер) — причины ~90% прошлых «сетевых ресетов».
2. **Деградация канала хост → AWS Dublin** — реальные «плохие окна» по несколько минут.
3. **Зомби-транзакции исчерпывали пул Supavisor** — усугубляло всё остальное.

## Факт 1: postgres.js ломается на смешении протоколов

- postgres.js 3.4.9 (последняя): после `select set_config(...)` простым протоколом
  **ответы на последующие запросы расширенного протокола в той же транзакции не приходят** —
  соединение висит ~20 c, потом ECONNRESET/CONNECTION_CLOSED.
- Воспроизводится вне Next, на любом порту pooler (6543 и 5432), на любой таблице.
- Без set_config extended-запросы работают; set_config + simple-запросы работают.
- Прошлая сессия «исправила» set_config через sql.raw (простой протокол) — это и
  создавало ядовитую комбинацию: данные ходят расширенным протоколом.
- **Решение: драйвер заменён на `pg` (node-postgres)** — та же последовательность
  через тот же pooler проходит стабильно (проверено отдельно от приложения).
- Миф «raw TCP стабилен, рвётся протокольный обмен → DPI» от прошлой сессии —
  для postgres.js случаев это был именно баг драйвера, а не сеть.

## Факт 2: канал действительно деградирует фазами (но это не главное)

- TCP-подключение к pooler всегда быстрое (~130 мс), TLS-рукопожатие тоже (~270 мс),
  HTTPS до supabase.co стабилен.
- В «плохую фазу» ответ на запрос (любой, даже `select 1`) может не прийти —
  клиент ждёт, сервер ждёт (`pg_stat_activity`: `ClientRead`). Пакеты теряются
  в обе стороны, в т.ч. посреди установленных соединений.
- Порог в плохую фазу: **~6 запросов на соединение** — после этого ответы не приходят.
  До порога — всё быстро (~70 мс/запрос). Порог плавающий (иногда падает и первый запрос).
- «Хорошие» и «плохие» фазы длятся минуты; пауза 90 c не гарантирует восстановление.
- Разделение «число запросов vs байты vs транзакция» не даёт устойчивого различия —
  в плохую фазу падает всё.

## Факт 3: зомби-транзакции душат пул (главный усилитель)

- Если транзакция застыла (потеря пакета посреди), сервер остаётся в
  `idle in transaction`. Клиент отваливается, Supavisor не замечает полузакрытый
  TCP — бэкенд занят «вечно».
- Накопившиеся зомби (наблюдалось 15 — это предел серверного пула) блокируют
  `BEGIN` всех новых соединений → **весь app виснет/падает с XX000**,
  даже `select 1` вне транзакции.
- **Лечение**: `pg_terminate_backend(pid)` по `pg_stat_activity where state =
  'idle in transaction' and xact_start < now() - interval '30 seconds'` —
  мгновенно восстанавливает работоспособность.
- **Профилактика** (вшито в lib/db/index.ts): `options: -c
  idle_in_transaction_session_timeout=30000` + `statement_timeout` +
  клиентский `query_timeout`.

## Что вшито в lib/db/index.ts (текущее состояние)

- Драйвер `pg` + drizzle `drizzle-orm/node-postgres` (заменил postgres.js).
- `maxUses: 1` — переиспользуемые из пула соединения умирают на первом запросе
  (проверено), поэтому каждое соединение используется один раз.
- `keepAlive: true`, `idleTimeoutMillis: 10s`.
- `statement_timeout: 10s` (сервер), `query_timeout: 6s` (клиент, обрывает
  ожидание потерянного ответа — раньше ждали ~15 c до kill от pooler).
- `options: -c idle_in_transaction_session_timeout=30000` — страховка от зомби.
- Клиент из пула берётся вручную (`pool.connect()`), вешается свой `on('error')`
  (иначе гибель сокета = uncaughtException), при сбое `release(true)`.
- До 6 повторов транзакции с backoff при connection-ошибках;
  `isConnectionError` обходит цепочку `cause` (drizzle оборачивает в
  «Failed query: ...»).
- Временные `[db]`-логи в `withUserDb` — убрать после отладки.

## Прочие изменения

- `lib/day.ts` (`getDayEntries`, `listDaySummaries`) и `actions/path.ts`
  (`getPathDay`): **запросы внутри транзакции только последовательно** —
  конвейер параллельных запросов (Promise.all) в одном соединении reliably
  зависает и плодит зомби. Цена: ~70 мс на запрос.
- Добавлен `pg` в зависимости, `@types/pg` в devDependencies.
- Диагностический маршрут `app/api/dbping/route.ts` и скрипты
  `scripts/probe-*.mjs` — **временные, удалить**.
- Миграции не трогались; схема и RLS не менялись.

# Дополнение (та же сессия, вечер 13 сентября 2026)

## Факт 4: startup-параметры pg НЕ проходят через Supavisor transaction pooler

- `options: "-c idle_in_transaction_session_timeout=30000"` (и `statement_timeout`)
  в конфиге Pool **отбрасываются** Supavisor в режиме transaction:
  `show idle_in_transaction_session_timeout` на таком соединении возвращает `0`
  (а statement_timeout — серверный дефолт 2min). Значит «страховка от зомби»
  из Факта 3 в приложении никогда не работала.
- Решение: обе настройки задаются внутри транзакции в `withUserDb` через
  `set_config('idle_in_transaction_session_timeout', '30000', true)` и
  `set_config('statement_timeout', '10000', true)` — проверено, применяется
  и автоматически сбрасывается после COMMIT (is_local=true, в пул не протекает).
- Следствие: зомби теперь живут ≤30 c вместо «вечно» — каскадное насыщение
  пула (15 бэкендов) больше не воспроизводится.

## Факт 5: порог деградации канала — round-trip'ы на соединение

- В плохую фазу соединение умирает после ~4-6 обменов; транзакция
  /history (BEGIN + set_config + 7 select + COMMIT = 10 round-trip'ов)
  не проходила НИКОГДА в плохую фазу, при 6 попытках — только error page.
- Транзакции из 4 round-trip'ов (BEGIN + set_config + 1 select + COMMIT)
  проходят в плохую фазу стабильно.
- Изменения:
  - `listDaySummaries` — один UNION-запрос вместо 7 select (1 round-trip);
  - `getDayEntries` (lib/day.ts) и `getPathDay` (actions/path.ts) — каждая
    выборка отдельной транзакцией на своём соединении, сборка Promise.all
    (параллель между РАЗНЫМИ соединениями безопасна; запрет Факта «секвентность»
    касался конвейера нескольких запросов в одном соединении);
  - после этого /history и /history/[date] открываются даже в плохой фазе.
- В хорошей фазе всё это также быстрее (меньше round-trip'ов).
